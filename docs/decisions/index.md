# 技术决策日志

> 记录关键技术决策及其背景，便于未来回溯。
> 格式：决策 → 背景 → 方案 → 结果

---

## D1: 批量采集从 iframe 改为 SPA 路由跳转

- **日期**：2026-03 Phase 1
- **背景**：最初使用 iframe 加载笔记详情页进行批量采集，但小红书的 CSP（内容安全策略）阻止了 iframe 加载
- **方案**：改为点击笔记卡片 → SPA 路由跳转到 `/explore/{noteId}` → 采集数据 → `history.back()` 返回列表
- **结果**：解决了 CSP 限制，但引入了虚拟列表 element 失效问题（卡片被卸载后需重新定位）
- **影响**：`batchController.js` 需要处理虚拟列表重定位逻辑

## D2: 弹窗关闭改用 chrome.debugger 模拟 Esc

- **日期**：2026-03 Phase 1
- **背景**：小红书弹窗关闭按钮的 class 名不稳定，`[class*="close"]` 匹配太模糊，容易误触其他元素
- **方案**：使用 `chrome.debugger.attach` + `Input.dispatchKeyEvent` 模拟 Esc 键关闭弹窗
- **结果**：稳定可靠，不依赖任何 class 名
- **代价**：需要 `debugger` 权限，用户首次使用时会看到"正在调试此浏览器"提示

## D3: 博主数据改用 `__INITIAL_STATE__` 代替 DOM 选择器

- **日期**：2026-03-20
- **背景**：博主页的 `.tag-item` 和 `.user-interactions .count` 等 DOM 选择器不可靠（页面结构中 `SPAN.shows` 只有文字标签，数值不在 DOM 中）
- **方案**：标签从 `userPageData.tags` 获取，关注/粉丝/互动数从 `userPageData.interactions` 获取
- **结果**：数据稳定，不再依赖不可靠的 DOM 选择器

## D4: 批量 TopN 改为"按点赞筛选、按页面位置执行"

- **日期**：2026-03-20
- **背景**：原方案按点赞排序后执行，导致采集器在列表中来回滚动定位，增加风控风险
- **方案**：先按点赞排序筛选出 Top N 候选，但执行时按笔记在页面中的原始位置顺序逐个采集
- **结果**：减少了来回滚动，降低风控触发概率

## D5: 默认不启用 BLOCK_MEDIA

- **日期**：2026-03-20
- **背景**：批量采集时屏蔽媒体资源（图片/视频）虽然加速了采集，但导致页面显示空白，用户体验差
- **方案**：默认不启用 `BLOCK_MEDIA`，让页面正常加载
- **结果**：页面不再空白，采集速度略慢但用户体验更好

## D6: 抖音当前视频识别从“猜 ID 优先级”转向“页面状态化上下文”

- **日期**：2026-03-26
- **背景**：抖音博主页视频弹层里，`vid`、`modal_id`、`activeVid`、`data-e2e-aweme-id` 会错峰变化。单纯叠加一套固定 ID 优先级，会导致“采到上一条/下载错条目”的循环问题。
- **方案**：先区分页面状态（博主页预览态 / 视频弹层态 / 直接视频页），再按当前状态解析上下文；在弹层态优先信 `modal_id + activeVid + data-e2e-aweme-id`，不再让 `vid` 覆盖当前弹层视频。
- **结果**：单条视频采集和下载不再主要依赖“猜哪一个 ID 更真”，而是围绕统一的当前视频上下文运行。
- **影响**：抖音单条采集、下载、评论、面板展示必须共享同一上下文解析层。

## D7: 抖音单条视频以“原生分享按钮点击”作为显式确认动作

- **日期**：2026-03-26
- **背景**：用户真实操作是“在视频弹层里上下滑动，然后对当前视频执行动作”。仅靠页面自动变化去猜“用户现在想采哪条”，稳定性很差。
- **方案**：把抖音原生分享按钮点击视为“当前视频显式确认动作”，插件在这一刻采集当前视频，并顺手记录分享文案与短链。
- **结果**：单条视频采集和下载的成功率明显提升，用户不需要理解技术细节，只要点分享即可“指哪打哪”。
- **影响**：后续涉及当前视频确认的动作，优先服从显式触发，而不是自动猜测用户意图。

## D8: 抖音批量视频采集从页面滑动/逐条打开改为作品列表 API 驱动

- **日期**：2026-03-27
- **背景**：抖音博主页连续滑动场景中，页面 DOM 复用和异步更新会让“打开第一条后再靠页面继续切换”非常不稳定；同时用户明确要求支持先扫描作品、按点赞排序再采集。
- **方案**：批量视频先走博主页作品列表 API，拿到 `aweme_id / 标题 / 点赞数` 等信息；若用户勾选 Top N，则先尽量发现足够多作品后再按点赞排序，最后按目标顺序逐条直接落库。
- **结果**：批量视频采集不再依赖页面滑动是否稳定，且对齐了小红书已有的“先发现、再排序、再执行”的业务逻辑。
- **影响**：批量视频能力的真实事实源已从 DOM 发现改为作品列表 API，相关文档与验收必须据此更新。

## D9: 抖音批量评论采集从“进入评论区页面”转为“作品列表 + 评论/回复接口 + 页面桥接”

- **日期**：2026-03-27
- **背景**：抖音评论接口更依赖页面态，单纯要求“先成功进入评论区页面”会让批量评论成功率很差；同时批量评论本质上是“先确定视频集合，再逐条抓评论树”。
- **方案**：先使用作品列表 API 确定视频集合，再对每条视频请求评论接口和回复接口；若页面上下文要求更强，则优先走页面桥接 fetch，失败再回退 Content Script 请求。
- **结果**：批量评论采集成功率显著提升，并且可以稳定保留评论与视频的归属关系及父子层级。
- **影响**：抖音评论链路后续应继续围绕“结构化接口优先，页面桥接兜底”的原则演进。

## D10: 将“半接入的抖音 webRequest 拦截链路”作为架构现实问题记录，而不是继续修幽灵文件

- **日期**：2026-03-27
- **背景**：回头看审查中反复出现的 review finding 指向 `src/platforms/douyin/apiInterceptor.js`，但当前真实代码树里并不存在这个文件；继续对一个幽灵路径做修复，会制造假闭环。
- **方案**：明确记录当前抖音实际生效的链路是页面桥接、页面侧 fetch、API capture 和 detail/works/comments 接口；若后续要恢复或引入后台拦截链路，必须以当前真实代码树为准重新建模与记录。
- **结果**：团队后续不再把“修 `apiInterceptor.js`”当作默认任务，而是先确认现行捕获链路和权限成本。
- **影响**：相关技术债会继续存在于治理清单里，但解决方式必须建立在当前真实架构之上。

## D11: 第二轮 content 首包治理暂缓，后续只在收益重新失衡时重启

- **日期**：2026-03-27
- **背景**：Wave 3 已经通过动态导入 `jszip`、抖音运行时拆分、数据运行时拆分，把 `content.js` 首包从 300+ KiB 压到约 185 KiB，并消除了构建告警。继续拆 Dexie、dashboard、导出链路会增加运行时复杂度和调试成本。
- **方案**：以“首包是否重新超过告警阈值、或新功能是否明显拖慢页面注入”为重启条件；在当前节点先停止第二轮加载边界治理，把精力转回数据回填、AI-ready 深化和产品化收口。
- **结果**：结构治理不再为了追求更小 bundle 持续拆分；当前异步 chunk（如 309.js / 323.js / 710.js）已足以支撑现阶段平台能力。
- **影响**：后续若新增功能再次推高 `content.js` 首包或引入明显注入延迟，再重开第二轮 bundle 治理；在此之前以稳定性优先。

## D12: 每轮测试改动后的文档同步改为硬门禁，而非“有空再补”

- **日期**：2026-03-29
- **背景**：最近多轮测试和修复都依赖大量上下文、页面事实和用户反馈。如果文档更新靠“最后想起来再补”，一旦会话中断或上下文丢失，高价值结论就容易停留在聊天里，无法进入长期可维护的事实源。
- **方案**：把“实现 + 测试 + 用户反馈”后的文档同步写入最高约束文件，并明确按变更类型更新对应权威文档：任何代码改动至少更新 `progress.txt`；用户可见变化同步产品文档；协议/字段变化同步技术文档；新策略和架构转向同步决策日志与活跃计划。
- **结果**：从这一节点开始，文档同步不再是可选补充项，而是工作闭环的组成部分；未同步文档的回合只能算“部分完成”。
- **影响**：后续所有功能修复、验收和治理，都必须在最终回复里说明本轮同步了哪些文件；如果故意不更新某个权威文件，也必须说明原因。

## D13: Wave 3 的加载边界必须持续守住，不能因为后续重构重新回到静态导入

- **日期**：2026-04-02
- **背景**：Wave 3 曾通过动态导入抖音运行时、内容数据运行时和 `jszip`，把 `content.js` 首包压到约 179~188 KiB。但接手检查时发现，`src/content/index.js` 又静态导入了 `douyinRuntimeModule.js` 与 `contentDataRuntime.js`，评论图片区链路也重新顶层导入了 `jszip`，导致 `content.js` 重新回弹到约 413 KiB。
- **方案**：把抖音运行时恢复为 `loadDouyinRuntime()` 按需加载；把内容数据运行时恢复为动态 `import('./contentDataRuntime.js')`；把评论图片区相关的 ZIP 打包依赖恢复为按需动态导入。
- **结果**：`content.js` 首包恢复到约 202 KiB，并重新产出异步 chunk；webpack 构建回到 `compiled successfully`。
- **影响**：后续所有结构重构都不能只看“文件是否拆小”，还必须检查是否破坏了加载边界；凡是把抖音运行时、数据运行时、ZIP 依赖重新静态打回首包的改动，都应视为性能回退。

## D14: 插件未来定位为“内容工作台的热插拔重执行端”，不再作为主系统演化

- **日期**：2026-04-02
- **背景**：当前插件已经具备网页内强执行能力，包括单条采集、批量采集、评论采集、评论图片区下载、页内任务控制等；但团队后续明确希望由“内容工作台”承担主产品职责，包括多人协作、统一数据库、账号与权限、任务历史、团队视图、在线 AI 工作流。
- **方案**：明确主从关系：内容工作台作为主系统，插件作为热插拔的重执行端；插件继续保留所有网页内采集与执行能力，但不再继续朝“主后台系统”方向扩张。未来任务以“工作台下发 -> 在线执行节点 -> 插件执行 -> 结果回传”为目标拓扑。
- **结果**：插件项目后续治理重点从“自己长出管理后台”转向“守住执行能力、任务状态语义、对外任务接入与结果回传边界”。
- **影响**：
  1. 插件仍应保留所有强执行链路，不应被削成轻上传器。
  2. 多人协作、权限、统一任务中心、AI 工作流主编排等能力应迁移到内容工作台。
  3. 插件侧未来新增能力应优先服务“被调度执行”和“结构化回传结果”。

## D15: 工作台接入插件时，外部任务协议应包裹现有内部消息总线，而不是直接暴露 `MSG.*`

- **日期**：2026-04-02
- **背景**：当前插件内部已经有较成熟的消息动作、页面上下文查询、任务状态语义和本地运行记录能力，主要落在 `src/shared/constants.js`、`src/content/messageHandlers.js`、`src/content/contentDataRuntime.js`、`src/db/collectionRunStore.js`。如果未来让内容工作台直接依赖这些内部动作名，短期会很快，长期会把插件内部实现直接冻结给外部系统。
- **方案**：保留插件现有 `MSG.*` 内部消息体系不动，在其外层增加“外部任务协议适配层”。工作台和在线执行节点只面向稳定的任务协议对象，例如 `task.envelope / capability.report / task.progress / task.result / task.failed / task.control`；插件收到这些对象后，再映射到内部动作和平台执行器。
- **结果**：插件内部实现仍可继续重构和治理，而工作台联调可以围绕一套独立版本化的协议推进；后续协议升级也能通过 `protocolVersion` 做兼容，而不需要外部系统感知每个内部动作名的变化。
- **影响**：
  1. 工作台不会直接耦合 `collectSingleNote`、`startBatchComments` 这类内部动作名。
  2. 插件后续协议建设重点会转到任务信封、能力握手、进度事件、结果包和错误包。
  3. `collectionRuns` 将成为远程任务和本地执行记录的映射枢纽，而不是单纯的本地日志表。

## D16: `contentDataRuntime` 不再强制追求异步 chunk，真实页面消息骨架以稳定优先

- **日期**：2026-04-02
- **背景**：Wave 3 曾把 `contentDataRuntime` 恢复为动态 `import('./contentDataRuntime.js')`，以减轻 `content.js` 首包。但在真实小红书页面联调中，Popup 可以正常读取 `chrome.runtime.getURL('845.js')`，而 content script 在执行 `GET_PAGE_CONTEXT` 时稳定报出 `Loading chunk 845 failed`，直接导致页面上下文查询、能力检查和远程任务派单失效。
- **方案**：保留 `douyinRuntime` 与 `jszip` 的按需加载，把 `contentDataRuntime` 改回主包静态加载。也就是说，后续加载治理不再遵循“所有运行时都异步化”，而是按职责区分：高频基础运行时优先稳定，平台重运行时与重依赖优先异步。
- **结果**：`contentDataRuntime` 不再依赖 content script 场景下的异步 chunk 加载，`GET_PAGE_CONTEXT`、Dashboard bridge、内容消息处理重新回到同一个稳定入口；同时避免把整套抖音运行时重新打回主包。
- **影响**：
  1. 后续任何针对 `content.js` 的体积治理，都必须先验证真实页面消息链和远程派单，再讨论是否继续拆 chunk。
  2. `contentDataRuntime` 应被视为“消息骨架”而不是普通可随时拆走的功能模块。
  3. 若未来要重新异步化内容数据运行时，必须先拿到真实页面联调证据，而不能只看 bundle 体积下降。

## D17: `douyinRuntime` 也不再强制保留异步 chunk，抖音真实执行链优先于体积优化

- **日期**：2026-04-02
- **背景**：在小红书侧修复 `contentDataRuntime` 后，真实抖音页面联调继续暴露 `Loading chunk 309 failed`。这次丢失的是 `douyinRuntimeModule.js` 对应的异步 chunk，直接导致 `douyin.batchNotes` 无法启动。说明内容脚本场景下，并不是只有“数据运行时”不稳，抖音运行时的异步加载也同样存在真实环境风险。
- **方案**：把 `src/content/douyinRuntime.js` 从动态 `import('./douyinRuntimeModule.js')` 改回静态导入，再通过 `loadDouyinRuntime()` 返回已加载模块。也就是说，当前阶段内容脚本里的关键运行时一律按稳定优先，不再把抖音执行链建立在异步 chunk 成功加载上。
- **结果**：`309.js` 不再作为独立 chunk 产出，抖音远程任务可以继续按真实页面执行链验证；代价是 `content.js` 回升到约 `341 KiB`，webpack 恢复出现 2 条体积 warning。
- **影响**：
  1. 当前阶段的 bundle 治理目标应从“继续拆 content 运行时”转向“寻找真正可以安全异步化的长尾依赖”。
  2. 若未来要重新把抖音运行时拆回异步 chunk，必须先证明 content script 场景下的 chunk 加载稳定，不可只凭本地构建体积决策。

## D18: 抖音视频下载路径从 `chrome.downloads.download` 回退到页面上下文 fetch，并移除 open-ended Range

- **日期**：2026-04-15
- **背景**：抖音视频下载连续出现 `SERVER_FORBIDDEN` / `Failed to fetch` 错误。诊断发现：1) 抖音播放器现在使用 `blob:` URL，`video.src` 不再是可直接下载的 CDN 直链；2) `chrome.downloads.download` 无法携带 `Referer`，而抖音 CDN 强依赖 `Referer` 鉴权；3) 页面 `origFetch` 携带 `Range: bytes=0-`（open-ended）时，所有 fetch/XHR 尝试均失败，疑似触发 CORS preflight 或被 CDN 直接拒绝。
- **方案**：
  1. `chrome.downloads.download` 对 Douyin 视频不再携带任何自定义 headers（它本来也带不了 `Referer`），仅作为快速尝试通道。
  2. 主要下载路径改回注入脚本（MAIN world）的 `origFetch`，优先尝试不带 `Range`、带 `Referer` 的配置；其次尝试 `omit`/`include` 两种 credentials；最后再带闭合 `Range`（如 `bytes=0-5242880`）降级。
  3. Content script 的 `fetch`/`XHR` 兜底、以及面板批量下载的 `noteMediaDownload.js` 同步移除 open-ended `Range`。
- **结果**：抖音视频下载不再把 `chrome.downloads.download` 当作主要通路，而是把“页面原生 fetch + 完整 cookie + Referer”作为核心路径；`Range` 头从默认配置中移除，避免 preflight/CDN 拒绝。
- **影响**：
  1. 后续任何 Douyin 媒体下载调试，若 `fetch` 仍失败，应优先检查 URL 新鲜度与 CORS 策略，而不是继续叠加 headers。
  2. `chrome.downloads.download` 对 Douyin 已证明不适合做“需要 Referer 鉴权”的下载，后续同类强鉴权 CDN 也应优先走页面上下文 fetch。

## D19: 小红书作者页建档不能只靠“到底确认”，必须主动触发底部加载并保留卡片封面

- **日期**：2026-04-28
- **背景**：内容工作台下发 `author_baseline` 首次建档目标是前 50 篇，但真实现场仍反复只回 28 条左右，且作品没有封面。复查后确认问题在插件作者页发现层：页面看起来到底时，继续加载有时需要额外的底部滚动/滚轮触发；同时卡片发现只保存作品 ID、标题、链接、点赞，没把卡片图传给工作台。
- **方案**：作者页到底且未达到目标数量时，插件继续发送底部加载触发并提高到底确认轮次；卡片发现阶段提取 `a.cover` 内图片作为 `cover / coverImg / coverUrl / images`；详情采集结果没有图片时，用卡片封面兜底。
- **结果**：首轮建档不再因为当前屏约 28 张卡片就提前收工；作品记录进入工作台时会尽量带封面。
- **影响**：后续处理小红书作者页“只采到首批卡片”的问题时，优先检查底部加载触发和虚拟列表累计逻辑；处理“无封面”时，先确认卡片封面是否已从发现阶段进入记录。

## D20: 工作台空闲接单必须遵守服务端退避，心跳不能绕过接单等待

- **日期**：2026-05-19
- **背景**：Vercel 免费资源异常消耗的主要压力来自插件/执行设备通道。新版插件虽然已经不走旧 `GET /api/collection-tasks` 接口，但后台每分钟心跳成功后仍会触发一次接单检查，导致服务端给出的空闲等待被部分绕过。
- **方案**：服务端在“无待处理任务”时返回约 2 分钟后再检查，能力不匹配也按 2 分钟等待；账号需要登录、受限、达到日上限或不可用时按约 5 分钟等待；抢单冲突、任务均衡和活跃任务续约仍保持短周期。插件后台记录下一次任务检查时间，空闲心跳只更新在线状态，不主动打断等待；已有活跃任务时继续短周期续约、控制同步和结果回写。
- **结果**：空闲工位不会因为心跳成功而频繁打 `claim` 接口，在线状态仍能保持，正在执行的监控、采集和数据同步任务不降频。
- **影响**：后续优化执行端成本时，先检查服务端 `nextPollAfterMs` 与插件后台闹钟是否一致；不能再把心跳当作无条件触发接单的入口。Web Push 可以作为下一阶段唤醒机制，但在没有落地前，低频智能轮询是正式兜底。

## D21: Web Push 只做任务唤醒，不替代接单与租约

- **日期**：2026-05-19
- **背景**：v2 低频轮询能止住空闲高频请求，但任务创建后仍需要等下一次轮询才会被发现。为了降低等待时间，同时避免回到高频轮询，需要由工作台在“真的有新任务或控制变化”时主动提醒插件。
- **方案**：插件通过 Chrome Web Push 注册订阅到工作台；工作台在采集控制台、监控中心、数据同步建单或任务控制变化时发送轻量 push。插件收到 `collection_task_available / collection_task_control` 后，只把下一次工作台接单检查提前，不直接执行任务、不信任 push payload 里的业务数据。
- **结果**：新任务可以更快被插件发现，但任务是否能领取、是否能运行、是否能回写，仍由原来的 `claim / lease / control / ingest` 链路判断。未配置 VAPID、推送失败或订阅过期时，v2 低频轮询继续兜底。
- **影响**：后续排查“插件没接到任务”时，先区分“push 是否叫醒”和“claim 是否拿到任务”。Push 只能缩短发现时间，不能绕过执行设备能力、账号健康、任务租约和服务器限流。

## D22: Content 消息处理器按职责拆分，工作台控制归口到 runtime

- **日期**：2026-05-25
- **背景**：`src/content/messageHandlers.js` 已经膨胀到近千行，数据读写、采集、远程控制、媒体下载和工作台结果打包混在同一个工厂里；同时 `src/content/index.js` 对无 `taskControl` 的 `WORKBENCH_TASK_CONTROL` 有一条绕过 runtime 的特殊停止路径，导致同类控制逻辑分散。
- **方案**：保留 `createContentMessageHandlers()` 的外部调用形态，把具体处理拆到 `messageHandlers/dataHandlers.js`、`collectionHandlers.js`、`workbenchHandlers.js`、`mediaHandlers.js`，并新增 `remoteControlRegistry.js` 管理远程任务暂停 / 继续 / 停止登记。`src/content/index.js` 不再直接处理工作台控制消息，而是统一交给 runtime 的工作台处理器。
- **结果**：调用方仍可从 `messageHandlers.js` 引入同一个门面函数；测试按职责拆成数据、采集、媒体、工作台和门面冒烟五组；旧式无 `taskControl` 的停止 / 暂停 / 继续消息仍能控制当前页面批量任务。
- **影响**：后续新增消息动作时，先按职责放入对应处理器；不要再把跨职责逻辑直接塞回 `messageHandlers.js` 或在 `content/index.js` 增加消息特殊分支。

## D23: 小红书搜索筛选后必须等待结果列表稳定，再开始采集

- **日期**：2026-06-01
- **背景**：小红书搜索页筛选点击成功后，结果列表刷新受网络和页面加载影响；如果插件立刻扫描，可能仍然读到筛选前的旧列表。
- **方案**：筛选点击并确认选中后，读取搜索页笔记流前若干真实笔记的稳定摘要，等待列表发生刷新并连续稳定，再进入批量笔记或批量评论扫描；如果页面迟迟不稳定，任务停在筛选阶段并提示刷新后重试。
- **结果**：批量采集不再把“筛选按钮已经选中”误当成“结果列表已经可采”，减少网络延迟下采错列表的风险。
- **影响**：后续所有搜索页筛选类能力，都应把“筛选状态确认”和“结果列表稳定”作为两个独立步骤；不能在筛选点击后立即打开笔记。

## D24: 本地打磨期插件默认联调本地工作台，不默认写线上正式站

- **日期**：2026-06-25
- **背景**：Mog 已将内容工作台数据库和 Blob 备份恢复到本机沙盒，接下来一周主要在本地打磨工作台、插件和数据库结构。插件如果继续指向正式站，会把采集结果、任务回传、媒体上传和工位同步写入线上数据，违背本地打磨目标。
- **方案**：本地打磨期间，插件工作台地址默认选择内置的“本地 3000”入口 `http://localhost:3000`；切到本地后，在本地工作台重新生成授权码或重新发起授权申请，连接成功后由工作台自动创建 / 复用工位，并先执行“测试连接”再采集或接单。只有用户明确要求线上 / 生产 / 正式站时，才切回 `https://lingganboom.fun`。
- **结果**：插件写入路径与内容工作台本地沙盒一致，普通同步、执行工位、采集任务回传和媒体上传都会进入本机 Docker 数据库和本地媒体目录。
- **影响**：后续排查“为什么本地没数据”时，第一步检查插件当前工作台地址是否仍是 `https://lingganboom.fun`；后续排查“为什么线上出现测试数据”时，第一步检查本地打磨期间是否误连正式站。

## D25: 插件授权与工位连接合并成一次动作

- **日期**：2026-06-25
- **背景**：旧流程要求用户先完成插件授权，再到工作台生成配对码并回到插件绑定工位。实际本地联调时，用户能看到工作台同意授权，但回到插件检查审批或输入配对码后没有明确反馈，形成“已授权但没工位”的半连接状态。
- **方案**：保留“工位”概念，但把工位创建从用户手动配对改成授权连接的后台结果。插件连接时带上本浏览器稳定 `stationKey`，工作台在授权码激活或审批领取时自动创建 / 复用工位，并返回 `stationId + stationToken` 给插件保存。配对码入口仅保留给旧版插件或自动连接失败修复。
- **结果**：用户只需要点击“连接插件”或“检查审批结果”；同一账号名下可以存在多个浏览器插件，每个浏览器插件自动拥有一个工位，默认名称按成员和浏览器生成，后续可在工作台改名。
- **影响**：后续不要再把“授权”和“绑定工位”设计成两个日常动作；排查插件无法接单时，先看连接结果是否返回工位身份，再看工位在线、接单开关和账号健康。

## D26: 出站协议根治——采集事实与任务结果解耦

- **日期**：2026-07-14
- **背景**：2026-07-13 写回事故：2.0.83 的 `normalizeOutboxRow` 落库时丢弃 `executionContext`，严格校验在发 HTTP 前把记录判成 `failed_terminal`，服务端收不到 RawSnapshot 直至租约过期；死信混入「待发送 2144」计数不可解释；测试只用内存 Map 从未覆盖真实 IndexedDB 边界（CTO 交接报告 §4-§9）。
- **方案**：①`executionContext` 原样持久化 + fake-indexeddb 真实 round-trip 回归测试（先红后绿）；②死信与待发送分账（`countsByStatus` / `listDeadLetters`），面板分开展示并提供导出；③新增 `captureJournal` 采集事实账本（v14，append-only，与租约解耦），record 在身份校验前先落账本；④恢复走只读导出（`EXPORT_OUTBOX_RECOVERY`）→ 工作台 `plugin_local_recovery` 显式导入，绝不把旧包绑新租约；⑤出站积压熔断 `OUTBOX_BACKLOG_BLOCKED`（仅可补发记录 >200 或最老未发送 >30 分钟时拒接新单并触发补发自愈；死信只告警，不计入数量阈值）；⑥采集进度传输层封顶 95%，100% 语义收归服务端终态确认。
- **结果**：v2.0.84。node --test 全绿（含新回归测试），构建通过。
- **影响**：以后任何插件发布必须过真实浏览器存储 + 服务端 ACK 的端到端验证，版本号不能作为唯一发布依据；服务端把最低版本升到 2.0.84 前必须先过单工位 canary（报告 §11 六门槛，Mog 拍板）；工位本地存量死信是恢复证据，禁止清理浏览器存储。
