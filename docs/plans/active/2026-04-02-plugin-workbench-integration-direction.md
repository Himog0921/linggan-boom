# 插件与内容工作台集成方向说明

> 文档类型：插件侧治理说明  
> 更新日期：2026-04-02  
> 目的：明确插件在未来系统中的角色，避免后续把插件继续演化成“主系统”

---

## 1. 本轮确认结论

未来系统形态已确认如下：

- **内容工作台** 是主产品和主系统
- **灵感爆爆爆插件** 是热插拔的重执行端
- 插件继续保留网页内采集体验与全部强执行能力
- 内容工作台未来可以向在线插件实例下发任务

因此，插件未来的角色不是“独立长成一个后台系统”，而是：

**一个可被调度、可在线执行、可回传结果的浏览器执行工具。**

## 2. 插件未来必须保留的能力

以下能力在未来不应轻易迁出插件：

1. 页内按钮与页内任务控制体验
2. 当前页面上下文识别
3. 单条采集
4. 批量采集
5. 博主采集
6. 评论采集
7. 评论图片区下载
8. 页面桥接、API 捕获、媒体下载
9. 暂停 / 继续 / 停止等强交互执行能力

原因：

- 这些能力天然依赖真实网页上下文
- 用户体验与页面状态紧密耦合
- 不适合直接搬进内容工作台网页端

## 3. 插件未来不应继续扩张成的东西

以下能力不应再以插件为中心继续膨胀：

1. 多人协作
2. 账号体系
3. 权限体系
4. 团队视图
5. 统一任务中心
6. AI 工作流主编排
7. 原始资料库的长期主视图

这些能力的系统归属，应放在内容工作台。

## 4. 插件与工作台的未来关系

未来建议按下面关系理解：

```text
内容工作台
  → 创建任务 / 分配任务 / 查看进度 / 接收结果 / 做 AI 工作流
    → 在线执行节点
      → 浏览器插件
        → 小红书 / 抖音页面执行真实采集动作
```

## 5. 插件侧未来最重要的新增边界

插件后续新增能力，应优先围绕下面三类边界建设：

### 5.1 任务接入边界

插件需要具备被外部任务系统安全触发的能力，例如：

- 接收关键词批量任务
- 接收博主采集任务
- 接收评论类任务

### 5.2 执行状态回传边界

插件需要把执行状态结构化回传，而不是只在本地页面提示成功/失败。

### 5.3 结果上送边界

插件未来不仅要保留本地数据能力，还要支持把结果回传给内容工作台。

## 6. 数据边界要求

未来工作台不是只收“整理后的选题”，而是要收两层数据：

1. 原始采集数据
2. 业务整理后的选题数据

这对插件意味着：

- 插件输出不能只面向当前本地 Dashboard
- 插件的结果结构应逐步朝“可远程消费”的统一协议收口

## 7. 当前阶段建议

在正式进入工作台联动前，插件侧接下来最重要的不是继续增加新的页面按钮，而是：

1. 守住现有执行能力稳定性
2. 守住消息协议和任务状态语义
3. 为未来任务下发 / 状态回传 / 结果上送预留清晰接口

## 8. 当前结论

从今天开始，插件项目的长期目标不应再被描述成：

- “继续把插件做成主系统”
- “插件内部自己长出完整管理后台”

而应被描述成：

- “内容工作台的可插拔重执行端”
- “保留真实页面执行力的采集前端”
