# 抖音能力进化计划（2026-03-27）

> 这份计划只围绕已经和用户确认过的真实业务场景，不再按“技术上能抓什么”倒推产品。
> 2026-03-27 晚间更新：其中“批量视频采集”“批量评论采集”已从规划推进到已实现状态；本文件当前更适合作为抖音业务规格与设计原则说明，不再单独承担实时实施状态的最高事实源。

## 1. 已确认的用户操作场景

当前用户是非技术背景，真实操作路径如下：

1. 进入抖音博主主页
2. 点开某一条视频
3. 在视频弹层里用鼠标上下滑动切换视频
4. 对当前视频执行采集、下载、分享、评论采集等动作

后续所有抖音功能，必须服从这条路径。

## 2. 已经验证稳定的能力

### 2.1 单条视频采集

- 当前视频可以通过明确触发动作稳定采集
- 原生分享按钮点击，已经可以作为“确认当前视频”的触发动作

### 2.2 单条视频下载

- 在分享触发确认当前视频后，单条视频下载已可用

## 2.3 2026-03-27 页面调研结论

本轮通过 Chrome MCP 和真实页面回放，确认了下面几条后续必须遵守的事实：

1. 博主页弹层场景下，当前视频应优先信 `modal_id + activeVid + data-e2e-aweme-id`。
2. 同一页面上的 `vid` 经常只是旧值或页面级预览值，不能覆盖弹层当前视频。
3. 评论和二级评论已有稳定接口，适合直接结构化采集。
4. 评论图片区高清图应优先走评论接口中的 `origin_url`，不要先依赖 DOM 放大图。
5. 抖音单条视频最稳的显式触发动作仍然是“原生分享按钮点击”。

## 3. 当前仍需继续产品化验收的能力

- 抖音单条评论采集体验
- 抖音评论区图片下载完整体验
- 抖音数据面板二次下载的长时效稳定性

## 4. 已确认的业务规格

## 4.1 批量视频采集

场景：

- 用户位于抖音博主主页
- 希望批量采集前 N 条视频的内容数据

要求：

- 逐条串行执行
- 支持暂停 / 继续 / 停止
- 失败跳过并记录失败清单
- 采集后的每条视频都要进入数据面板
- 数据面板中必须支持“二次下载视频”
- 媒体预览优先显示封面即可

关键验收：

- 批量采完后，任意一条视频都能从数据面板再次点击下载
- 若旧直链失效，系统应尽量基于 `videoId` 再刷新一次直链后下载

## 4.2 单条评论采集

场景：

- 用户已经打开某条抖音视频弹层
- 点击插件里的“采集评论”

要求：

- 只采当前视频
- 支持评论数量上限
- 不填即采全部
- 包含一级评论与二级评论
- 明确保留父评论和子评论层级关系

## 4.3 批量评论采集

场景：

- 用户位于抖音博主主页
- 想批量采集前 5 / 10 / 20 条视频的评论

要求：

- 视频数量支持 5 / 10 / 20
- 每条视频的评论上限由用户填写
- 不填表示采全部
- 包含二级评论
- 必须知道每条评论对应哪条视频
- 必须保留父评论与子评论层级关系
- 支持暂停 / 继续 / 停止
- 失败跳过并输出失败清单

## 4.4 评论区图片下载

场景：

- 用户打开某条抖音视频评论区
- 希望下载评论区里的高清图片

要求：

- 行为与小红书评论图片下载保持一致的产品体验
- 尽量拿高清图
- 排除头像、表情、装饰性小图
- 下载结果与当前视频绑定

## 5. 产品原则

### 5.1 明确触发，不自动猜意图

不再默认“滑到哪里就自动知道用户想采哪条”，而是要求明确触发动作：

- 单条视频：分享按钮 / 采集按钮 / 下载按钮
- 单条评论：采集评论按钮
- 批量任务：批量按钮 + 设置弹窗 + 任务控制台

### 5.2 单一事实来源

采集、下载、评论、数据面板都必须共享同一份“当前视频上下文”。

### 5.3 批量任务可控

所有批量任务都必须具备：

- 数量设置
- 进度展示
- 暂停 / 继续 / 停止
- 失败跳过
- 结果汇总

## 6. 开发顺序

### Phase B：抖音单条评论能力

- 实现单条评论采集

- 完成真正可控的批量视频采集

### Phase D：抖音批量评论能力

- 基于单条评论能力与批量视频遍历能力，完成批量评论采集
