# 2026-03-30 项目综合诊断报告

> 诊断范围：产品功能、技术架构、数据底座、设计与交互、稳定性、性能、业务匹配度  
> 诊断依据：当前代码现实、`progress.txt`、`docs/product/*`、`docs/technical/*`、近期用户验收结果、既有 MCP 页面调研与真实截图反馈  
> 说明：本报告聚焦“当前真实状态”，不重复早期历史设计假设

---

## 1. 结论先行

当前项目已经跨过了“功能原型”阶段，进入了“可持续迭代的多平台采集产品”阶段。

如果用一句话概括当前状态：

- **功能完成度**：约 80% 到 85%
- **用户可用度**：高于功能完成度，核心主链路已经能让真实用户获得价值
- **工程成熟度**：中等偏上，治理意识已经形成，但还没完全收口
- **下一阶段重点**：不再是“大量补功能”，而是**稳定性、体验统一、数据产品化、性能治理**

当前最值得肯定的，是我们已经把很多最难的问题从“平台黑盒猜测”转成了可维护的系统：

1. 采集、批量、评论、评论图片区、面板、导出已经不是彼此孤立的功能点。
2. 小红书与抖音的任务体验正在从两套思路收口为同一套任务模型。
3. 数据模型已经具备本地管理和后续 AI 分析的雏形。
4. 项目规则、验收与文档同步机制已经真正写入最高约束层。

但项目还没有到“高枕无忧”的状态。当前最核心的问题不再是“会不会采”，而是：

- 是否在所有支持场景里都能**稳定、明确、可预测**地完成任务
- 是否能让用户在不懂技术细节的情况下理解“当前能做什么、正在做什么、为什么失败”
- 是否在继续扩展功能前，先收住架构复杂度和交互复杂度

## 2. 当前功能版图

### 2.1 小红书

**已基本跑通**
- 单篇笔记采集
- 单篇评论采集
- 博主采集
- 批量笔记采集
- 批量评论采集
- 评论图片区下载
- Dashboard 查看、导出、媒体下载

**当前特征**
- 核心单篇与批量链路已经比较成熟
- 页内任务控制台体验明显优于抖音
- 评论图片区下载从用户视角已经接近“可用”

**仍待优化**
- 批量评论在不同页面类型上的一致性仍需继续关注
- 批量笔记与批量评论速度还有优化空间
- 页面提示与设置弹层仍有视觉层级不统一问题

### 2.2 抖音

**已基本跑通**
- 单条视频采集
- 单条视频下载
- 分享触发采集
- 单条博主采集
- 博主页批量视频采集
- 搜索页批量视频采集
- 博主页批量评论采集
- 搜索页批量评论采集
- Dashboard 中的记录查看与部分二次下载

**当前特征**
- 抖音最难的“当前视频是谁”问题，已经从早期的 ID 猜测，转向“页面状态 + 动作确认”
- 搜索场景、详情页、博主页、弹层页的差异已经被显式建模
- 评论接口与详情接口已经具备较稳定的页面桥/接口桥能力

**仍待优化**
- 评论图片区下载体验仍然是长尾高风险点
- 搜索页和详情页混合态下，仍然需要更强的“页面能力拒绝机制”
- 页内按钮、任务提示、设置弹层的 UI/UX 还不够成熟

## 3. 真实业务需求与当前满足度

从真实使用角度看，这个插件的需求不是“尽可能多抓字段”，而是下面这四类：

### 3.1 快速确认当前内容并采集

用户需求：
- 我看到一条内容，想马上把它采下来
- 需要知道采的是不是我眼前这一条

当前满足度：
- **小红书：高**
- **抖音：中高**

判断：
- 小红书详情页单篇链路更自然
- 抖音必须依赖页面类型和动作确认，已经明显改善，但复杂度仍高于小红书

### 3.2 批量获取一批内容/评论

用户需求：
- 我想在博主页或搜索页快速抓一组内容
- 可以按顺位，也可以按 Top N
- 不想自己一条一条点

当前满足度：
- **小红书：高**
- **抖音：中高**

判断：
- 这块已经从“功能尝试”进入“真正可用”
- 但抖音搜索页和混合页仍需要更强的 page gate

### 3.3 获取评论素材与评论关系

用户需求：
- 评论不只是文本，要能看到层级、归属、搜索词关联
- 评论图片区下载的目标是“素材”，不是为了顺带采评论

当前满足度：
- **评论结构：中高**
- **评论图片区：中**

判断：
- 数据结构已经走在前面
- 产品体验还没有完全跟上，尤其是“扫描 / 下载 / 打包 / 停止”的语义

### 3.4 数据面板回看、导出、分析

用户需求：
- 采完后能看懂
- 能导出
- 能重新下载媒体
- 后面可用于 AI 分析

当前满足度：
- **数据面板：中高**
- **AI-ready：中**

判断：
- 面板已经有数据管理能力
- 但离“分析工作台”还差一段，尤其在可读性、字段分层和资产管理视图上

## 4. 技术诊断

## 4.1 当前架构的优点

1. **平台分层已经成型**
- `src/platforms/xhs/**`
- `src/platforms/douyin/**`
- 平台差异开始进入各自目录，而不是混在一个总文件里

2. **内容脚本主入口已明显收口**
- `src/content/index.js` 现在只有 261 行
- 这说明此前“大一统入口”最危险的阶段已经过去

3. **任务模型已经形成统一方向**
- `collectionRuns`
- 右下任务控制台
- 顶部通知条
- 批量与单条任务开始共享阶段语义

4. **数据模型已经具备统一化意识**
- `notes / comments / authors / collectionRuns / mediaAssets`
- `contentId / platformContentId / authorEntityId`
- `handle / raw* / collectorVersion`

5. **对黑盒平台的策略在变成熟**
- 不再单靠 DOM
- 会结合接口、页面桥、动作确认、上下文稳定判定

## 4.2 当前架构的脆弱点

1. **复杂度转移，而不是消失**
- `content/index.js` 变轻了
- 但复杂度转移到了：
  - `src/popup/popup.js`（988 行）
  - `src/dashboard/dashboard.js`（960 行）
  - `src/platforms/douyin/index.js`（774 行）
  - `src/platforms/douyin/videoCollector.js`（738 行）
  - `src/platforms/douyin/commentCollector.js`（663 行）

这说明项目已经从“主入口过胖”转向“控制器/交互面过胖”。

2. **任务控制与业务逻辑仍耦合较重**
- 评论采集
- 评论图片区
- 批量视频
- 批量评论  
这些都还混杂了：
- 阶段管理
- UI 更新
- 数据写入
- 页面操作

3. **页面类型判断仍然是高风险点**
- 小红书：搜索页 / 详情页 / 弹层页
- 抖音：博主页 / 搜索页 / 详情页 / 弹层页 / 搜索视频详情混合页  
一旦判错，就会出现“功能存在，但走错链路”。

4. **媒体链路比数据链路更脆弱**
- 数据可以靠最小记录兜底
- 媒体不行，媒体一旦失败，用户就会直接感知“这条功能没成”

5. **文档治理虽已成型，但仍依赖执行纪律**
- 规则已经写进 `AGENTS.md / CLAUDE.md`
- 但只要某一轮偷懒不更新，项目仍会漂移

## 5. 稳定性诊断

### 5.1 当前已经明显稳定下来的部分

- 小红书单篇采集
- 小红书批量笔记
- 小红书评论图片下载主流程
- 抖音单条视频采集
- 抖音分享触发采集
- 抖音搜索页/博主页批量评论主链路
- 抖音搜索页/博主页批量视频主链路

### 5.2 当前仍属于高风险的部分

- 抖音评论图片区下载
- 小红书/抖音评论任务的停止语义
- 页面混合态下的入口显示与能力拒绝
- 搜索页与详情页混合态的场景切换

### 5.3 稳定性上的根问题

当前稳定性问题，主要不是“接口不稳定”，而是：

1. 页面类型不够单纯  
2. 长任务语义不够清晰  
3. 媒体链路比文本链路更脆弱  
4. UI 提示和真实执行阶段有时不一致

## 6. 性能诊断

### 6.1 当前硬指标

最近构建结果：
- `content.js`：约 **412 KiB**
- `background.js`：约 **115 KiB**
- `popup.js`：约 **23.1 KiB**
- `dashboard.js`：约 **21.9 KiB**

Webpack 仍给出：
- asset size warning
- entrypoint size warning

### 6.2 这意味着什么

`content.js` 偏大，目前不是“立刻坏掉”的问题，但会带来 4 类隐性成本：

1. 页面注入更慢
2. JS 解析与执行更重
3. 重页面里更容易卡顿
4. 后续继续加功能时更容易相互牵连

### 6.3 慢的主要来源

不是一个点造成的，而是多因素叠加：

- Dexie（约 92.5 KiB）
- JSZip（约 95.3 KiB）
- content runtime 中平台逻辑和任务逻辑仍较多
- 页内注入 + 弹层 + 任务控制台 + 下载链路同时存在

### 6.4 当前性能判断

- **不是当前最高优先级阻塞**
- **是明确的下一阶段优化项**

一句话：
项目现在“能用且值钱”，但如果再持续加功能而不控体积，后面会慢慢演化成新的稳定性问题。

## 7. 数据与 AI-ready 诊断

### 7.1 数据底座的优点

当前数据层已经明显不是“随手存几个字段”的阶段了：

- `notes`
- `comments`
- `authors`
- `collectionRuns`
- `mediaAssets`

而且统一化字段已经具备：
- `contentId`
- `platformContentId`
- `authorEntityId`
- `collectionRunId`
- `handle`
- `rawPayload / rawDomText / rawShareText / rawUrl / rawSource`

### 7.2 当前 AI-ready 仍未完全到位的地方

1. 历史数据回填还没完全完成
2. 并不是所有链路都完整消费了 `collectionRuns / mediaAssets`
3. 评论图片区素材的管理还没有形成独立视图
4. 分析层视角还弱，更多仍是“记录层视角”

### 7.3 结论

当前数据底座：
- **足够支撑本地管理和基础导出**
- **足够作为 AI 分析的前置原料**
- **还不够成为真正成熟的数据工作台**

## 8. 设计与 UX 诊断

### 8.1 当前做得好的地方

1. **页内任务控制台开始统一**
- 小红书已经明显更像一款产品，而不是工程调试工具

2. **Popup 的信息架构方向是对的**
- 当前页面
- 当前内容
- 批量任务
- 工具区  
这是一个正确的骨架

3. **用户越来越能理解“任务是什么、在哪管理”**
- 这是整个项目 UX 最关键的进步

### 8.2 主要问题

1. **视觉系统还不够成熟**
- 当前黄黑高对比风格有辨识度
- 但排版、字号、按钮尺寸、留白、图标精度还不够统一

2. **某些弹层还像“功能表单”，不像“任务设置器”**
- 尤其是批量设置弹层
- 信息顺序和控件关系还不够自然

3. **抖音页内右侧面板与任务提示仍显得像两套产品**
- 用户会觉得“面板是一个东西，任务条又是另一个东西”

4. **Dashboard 仍然过于工程化**
- 列太多
- 层级不够明确
- 原始字段和分析字段混在一起

5. **部分文案还停留在开发者语气**
- 比如“批量评论 / 批量视频 / 采集当前评论”这些动作名虽然准确，但不够说明“会发生什么”

### 8.3 UX 评价

当前 UX 已经不是“差”，而是：
- **主流程可理解**
- **复杂流程仍显笨重**
- **离成熟产品还有一层产品设计精修**

## 9. 用户满意度判断

如果从“用户是否能真正完成主要目标”来判断：

### 9.1 已经能让用户满意的部分

- 小红书主链路
- 抖音视频主链路
- 批量采集主能力
- 搜索词关联、评论层级、批量 Top N 这类高价值能力

### 9.2 仍会伤害满意度的地方

- 评论图片区的速度与停止语义
- 某些页面虽然支持，但用户不知道自己是否在正确页面
- Dashboard 还不够“分析友好”
- UI 排版与弹层精度不够，容易给人“功能很强，但产品还比较粗”这种感受

### 9.3 综合判断

当前项目已经能明显提供价值，但还没有到“细节让人放心”的状态。

从用户视角看，这不是“做没做出来”的问题，而是：

- **值不值得长期用**
- **在压力场景下还敢不敢信任它**

这也是下一阶段真正要解决的事。

## 11. 总评价

如果只看“代码写了多少”，这个项目已经不小。  
如果看“产品有没有开始成型”，答案也是：**已经成型了**。

这次最难得的，不是功能堆起来了，而是项目终于开始具备了下面这几个长期价值：

- 有真实的用户操作模型
- 有明确的任务模型
- 有可追溯的数据模型
- 有文档硬门禁
- 有逐步成型的跨平台体验

所以我对当前项目的判断是：

**它已经不是一个实验性采集插件，而是一个接近可维护产品的浏览器扩展。**  
下一阶段不再应该以“多做几个功能”为荣，而应该以：

- 更稳定
- 更清楚
- 更一致
- 更值得信任

作为主目标。
