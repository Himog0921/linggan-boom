## 2. 当前用户真正的需求是什么

从这轮大量来回测试可以反推出，用户的真实需求并不是“页面上多几个按钮”，而是 4 类更本质的目标：

### 2.1 可靠采集

用户不关心 DOM、接口、弹层还是详情页。用户只关心：

- 我现在看到的这条内容，是不是就是被采到的这条
- 批量采的时候，是不是采的是我眼前这一组
- 采完之后，媒体还能不能再下载

### 2.2 可理解的长任务

用户对“批量评论、评论图片区、批量视频”的核心需求是：

- 现在在做什么
- 能不能暂停
- 停止以后还会保留什么
- 为什么成功 / 为什么失败

### 2.3 数据可用于后续分析

用户已经明确把后续 AI 分析作为场景之一，因此数据不能只满足“面板里看起来有值”，还必须满足：

- 视频 / 评论 / 作者之间能稳定关联
- 搜索词、任务上下文能落到记录里
- 评论层级关系可追溯
- 媒体资产可重复利用

### 2.4 双平台体验尽量一致

用户已经多次明确：抖音和小红书虽然技术实现不同，但用户的操作心智没有本质区别。

所以真正高价值的方向不是“平台特判越来越多”，而是：

- 不同平台的技术差异藏在实现层
- 用户面对的是统一的任务模型和统一的表达方式

## 4. 产品层诊断

### 4.1 当前做对了什么

1. **平台能力边界已经清晰**
   - PRD 与 APP_FLOW 已经开始能反映真实产品流，而不是只描述理想功能

2. **任务模型开始统一**
   - Popup、页内任务条、评论弹层、批量弹层逐步围绕“单条 / 批量 / 图片区 / 下载”分层

3. **搜索场景真正进入了产品定义**
   - 不是只支持主页
   - 而是开始承认“搜索结果页”是用户的重要数据场景

4. **AI 分析诉求已经进入产品设计**
   - 搜索词关联
   - 评论树层级
   - 任务上下文
   - 媒体资产

### 4.2 当前产品层最大问题

1. **功能数量已经超过信息架构承载力**
   - Popup 里“当前页面 / 当前内容 / 批量任务 / 工具区 / 飞轮工作台”已经开始拥挤

2. **任务语义仍有残余不一致**
   - 单条任务、批量任务、评论图片区下载的“停止”语义仍然容易引起误解

3. **平台差异仍然泄漏到用户体验**
   - 抖音搜索页、视频详情页、博主页；小红书详情页、搜索页、列表页
   - 用户仍在被迫理解这些页面类型

4. **“可执行”与“可理解”之间还有差距**
   - 很多能力已经能用，但第一次使用的理解成本仍高

### 4.3 业务上的核心机会

如果从业务角度看，当前插件已经不只是“采集器”，而是在向“本地灵感数据工作台”发展。

真正值得放大的价值是：

- 选题与素材发现
- 搜索场景的内容对比
- 评论语义与图像素材收集
- 跨平台内容样本积累
- 面向 AI 的本地资料整理

这意味着下一阶段的产品策略不该再只围绕“再加一个采集按钮”，而应该转向：

- 让采集结果更容易被理解和复用
- 让任务更稳定、更可解释
- 让面板更像工作台，而不是数据仓库前端

- 搜索页 / 弹层页 / 详情页的上下文识别

## 6. 数据层诊断

### 6.1 当前数据层的真实优点

当前数据模型已经不是简单的“采集到什么存什么”，而是开始形成分析基础：

- `contentId / platformContentId`
- `authorEntityId`
- `collectionRunId`
- `rootCommentId / level / replyTo...`
- `searchKeyword / searchPageUrl`
- `collectorVersion / raw*`

这说明方向是对的。

### 6.2 当前数据层的现实问题

1. **AI-ready 是“可起步”，不是“已成熟”**
   - `DATA_MODEL.md` 自己也承认了这一点
   - 当前更像：采集层和分析层之间的过渡模型

2. **导出层仍然有较强硬编码痕迹**
   - `src/content/messageHandlers.js` 里 CSV 头部字段仍是长数组硬编码
   - 这会让字段演进成本持续变高

3. **媒体数据与内容数据还没有完全形成统一叙事**
   - `mediaAssets` 已经存在，但用户侧的“媒体资产”还没有成为清晰的一层产品能力

4. **历史数据回填与新数据规范化并存**
   - 当前是务实做法
   - 但长期看，需要更明确的“读时兼容 / 写时规范 / 批量维护”的边界

### 6.3 从业务与 AI 视角看，当前数据是否“够用”

结论：

- 对“本地管理 + 基础分析 + 导出给 AI 做二次处理”来说：**基本够用**
- 对“直接做稳定的自动化分析产品”来说：**还不够**

缺口主要在：

- 原始证据层继续补齐
- 媒体资产语义统一
- 评论深度和采集策略显式记录
- 更稳定的导出契约

     - 标题过大
     - 输入控件过重

4. **状态反馈仍有重复**
   - 顶部条
   - 右下任务条
   - 当前作品提示
   三者关系仍然可以继续收敛

5. **图标体系不统一**
   - 仍有 Emoji、文本、不同风格图标混用
   - 这会拉低产品完成度

## 8. 稳定性与性能诊断

### 8.1 稳定性

当前稳定性已经比中期迭代时好很多，但仍呈现出“主链路稳、边缘场景敏感”的结构：

**主链路相对稳**
- 小红书单篇 / 批量
- 抖音单条 / 批量主页
- 搜索页核心批量能力

**边缘链路更敏感**
- 评论图片区
- 搜索结果页的批量场景
- 详情页 / 弹层页切换
- 长任务的中断与恢复语义

### 8.2 性能

当前最明确的性能问题有两个：

1. **内容脚本首包过大**
   - `content.js` 412 KiB
   - 这会增加页面注入、解析、执行成本

2. **评论图片区任务结构较重**
   - 慢的不只是网速
   - 还包括：
     - 扫描评论树
     - 拉原图
     - 组装 zip
     - 状态同步

### 8.3 对用户的真实影响

如果从用户感知出发，最容易被感知到的性能问题不是“Webpack 告警”，而是：

- 按钮出现略慢
- 长任务反应慢
- 设置弹层笨重
- 评论图片区下载“明明发现了图片，但感觉迟迟没完成”

所以性能优化要优先服务这些体验，不要只追求体积数字好看。

这是一个已经完成了“从脚本到产品雏形”转变的项目。

- 用户能不能更顺畅地使用这些功能

所以如果给一句总判断：

**项目已经证明了可行性，接下来最重要的不是继续横向加功能，而是纵向提升完成度。**

- UI/UX 收口
- 长任务稳定语义

而不是再盲目增加新按钮。
